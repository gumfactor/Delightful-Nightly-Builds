# Manual — Fleet Drift

A cross-repo dependency version drift dashboard: run it against your own GitHub account and see, in one place, which third-party dependencies are pinned to different versions across the repos you own, and how far behind each pin is from its real latest release.

## Setup

```bash
cd builds/2026-09-01-fleet-drift
pip install -r requirements.txt   # only needed to run the test suite (pytest)
```

Fleet Drift itself needs no third-party packages to run — only the standard library. `pytest` in `requirements.txt` is for running the test suite, not for using the tool.

You need a GitHub personal access token with at least `repo` (or, for a fine-grained token, read access to Contents and Metadata) scope on the repos you want scanned:

```bash
export GITHUB_TOKEN=ghp_your_token_here
```

## Commands

### `sync` — fetch the current state of every owned repo

```bash
python main.py sync
```

Lists every repository your `GITHUB_TOKEN` owns, reads `requirements.txt` and `package.json` from each repo's default branch, looks up each dependency's real latest version on PyPI or the npm registry, and saves a dated snapshot to a local SQLite database (`fleet_drift.db` by default — pass `--db path/to.db` to use a different file). Running `sync` again on the same UTC day updates that day's snapshot in place; running it on a later day adds a new day to the history so drift trends accumulate over time.

### `list` — quick terminal summary

```bash
python main.py list
```

Prints the latest sync's drift findings straight to the terminal — no HTML needed if you just want a quick check.

### `render` — build the dashboard

```bash
python main.py render --output fleet_drift_report.html
```

Writes a self-contained HTML dashboard (open it directly in any browser, no server needed) with:
- Hero stats: repos scanned, unique dependencies tracked, how many are drifted, how many of those are major-version drift.
- A **drift matrix** — every dependency pinned to more than one version across your repos, with a severity badge and the exact per-repo versions. Sortable by clicking a column header, filterable by the search box.
- A **most-drifted dependencies** chart (falls back to a plain table automatically if the Chart.js CDN is unreachable — nothing breaks offline).
- A **per-repo staleness panel** — which repos are carrying the most dependencies behind their latest release.

Add `--ai` to include a one-paragraph "what to fix first" note generated by Claude Haiku:

```bash
export ANTHROPIC_API_KEY=sk-ant-...
python main.py render --ai
```

Without `ANTHROPIC_API_KEY` set, `--ai` still works — it just uses a deterministic template built from the same numbers instead of calling the API. No network call is ever made to Anthropic without a key present.

### `history` — one dependency's pinned-version history

```bash
python main.py history python requests
python main.py history npm react --json
```

Shows every recorded snapshot of a given dependency (first positional argument is the ecosystem — `python` or `npm`) across every sync you've run, oldest first.

## Reading the dashboard

- **Severity badges** — `major`/`minor`/`patch` describe how far apart the most-behind and most-current pinned versions are across your repos, using semantic versioning: a major-version gap (e.g. `3.2.0` vs `5.1.0`) usually means a real breaking-change risk if you deploy the older repo without testing against the newer API; a patch-version gap is usually safe to ignore.
- **"Versions in use"** lists every repo pinning that dependency and at what version, so you know exactly which repo(s) to update to converge.
- **Per-repo staleness** is independent of drift — a dependency can be pinned identically everywhere (no drift) and still be several versions behind its real latest release everywhere (high staleness). Both matter for different reasons: drift is an internal-consistency risk, staleness is a "you're missing fixes/features upstream" signal.

## Running the tests

```bash
python -m pytest tests/ -v
```

All 99 tests run against injected fake HTTP transports — no test ever makes a real network call, so the suite runs identically with or without network access.
